# Engine decision catalogue (AsyncTI4 component ids)

Generated by `tools/engine-catalog/generate.py` (hand-written prose lives in `tools/engine-catalog/notes.md`;
tables are regenerated). Machine-readable data: `docs/engine-catalog.json`.

**Scope:** <!-- STATS -->

Every entry in `engine-catalog.json` is one registered handler prefix, with: handler class/method/file/line,
`save` flag, how the handler parses the id (`parseOps`, `resolvesFromId`), the id grammar seen at creation
sites (`grammar.patterns`, `grammar.fields`), creation sites (`createdAt`), labels, who is asked
(`target`), game `area`, `content` (core / homebrew / Thunder's Edge / Discordant Stars / Twilight's Fall /
fog of war), the proposed decision `kind`, and the owning `agent`.

## How the bot routes ids (what we are replacing)

- **Buttons:** `ButtonListener` -> `ButtonProcessor.queue` -> `HandlerRegistry.resolve(customId)`. The registry is
  built by reflection from every `@ButtonHandler("prefix")` method (2,600+), and dispatch is a **longest-prefix match**
  over the id (`HandlerRegistry.findMatchedKey`). There are no `startsWith` chains left in `ButtonListener`; the
  remaining chains live *inside* handlers that own a short prefix and sub-route (see hard cases).
- **Envelope** (`ComponentIdEnvelope.decode`), applied before matching:
  - `FFCC_<faction>_` = owner. `ListenerContext.isPressedByOwner` rejects anyone else ("these buttons are for
    someone else"). Exceptions: `firmament` buttons may be pressed by `obsidian`, and Onyxxa granted holders.
  - `dummyPlayerSpoof<faction>_` = act as that NPC/dummy player (`Player.factionButtonChecker()` returns this for
    NPC/dummy seats instead of `FFCC_`).
  - `deleteThisButton` / `deleteThisMessage` anywhere in the id = delete the button / the message before handling.
- **Selects:** `SelectionMenuProcessor`, same registry over `@SelectionHandler`, then the legacy
  `SelectionManager` list (`SelectFaction`, `BigSelectDemo`).
- **Modals:** `ModalListener`, registry over `@ModalHandler`, then a hard-coded `jmfA_` fallback into the settings
  framework (`MiltySettings`, `DraftSystemSettings`, `FrankenSettings`, `BaseGameMiniMiltySettings`).
- Handlers get `(event, Game, Player presser, String id, MessageChannel)` injected; `save=false` handlers run under a
  read lock and do not save.
- The presser is always the acting player. Nothing in the routing layer says who *should* press a button unless the
  id carries `FFCC_`. That is the main problem for a typed Decision stream: the target player has to come from the
  creation site.

## Target player: how to resolve it

`target.summary` per handler (counts in the tables below):

| value | meaning | Decision-stream treatment |
|---|---|---|
| `explicit:ffcc` | every creation site prefixes `FFCC_<owner>_`. `target.ownerVars` names the Java receiver. `player` is the actor of the creating method; `target`/`opponent`/`p2`/`owner`/`agentOwner` means someone else is being asked (for example the defender in combat or the owner of a PN) | target = owner faction from the id; trivially exact |
| `explicit:private-thread` | posted to `player.getCardsInfoThread()` (the player's `#cards-info` thread) | target = the thread owner |
| `explicit:ephemeral-to-presser` / `presser-modal` | ephemeral reply or modal in response to a press | target = presser of the parent decision (a sub-step, not a new decision) |
| `each-player` | reaction/follow/vote window: SC follow, whens/afters, sabotage, voting, riders, "end turn when all reacted" | one decision **per eligible player**, answered in parallel; the engine must expose who is still pending (the bot tracks this in stored values and message reactions) |
| `implicit:actions-channel+mention` | main/actions channel (`getCorrectChannel()` = private channel in FoW), message mentions a player | target = the mentioned player; the generator cannot tell which mention, so look at `createdIn` |
| `implicit:same-channel-as-press(inherits)` / `edit-in-place` | follow-up step posted (or edited) where the previous button was pressed | target = presser of the previous step |
| `implicit:actions-channel(anyone)` | no owner, no mention: any player (often host/speaker in practice, for example `agendaResolution_`, `proceedToVoting`, `resolveWithNoEffect`) | needs a rules decision: speaker, active player, or "any" |
| `mixed` | some creation sites are explicit, some are not | treat the explicit sites as authoritative and fix the others when migrating |
| `unknown` | no creation site resolved (id built from a parameter several calls away, or by a framework such as `jmfA_`/`jwds_`/`fowSetup*`) | resolve by hand |

Practical rule for the engine: **when a decision is raised, record `forPlayer` at raise time** (the `Player` whose
`factionButtonChecker()` is used, the owner of the cards-info thread, the mentioned player, or "each player in
order X"). Do not try to recover it from ids afterwards.

## Hard and ambiguous cases

1. **State kept in Discord, not in Game.** 26 handlers read `event.getButton().getLabel()` and 30 read the message
   text (`getContentRaw`). Examples:
   - `exhaust_` (agenda voting, `AgendaHelper.exhaustStuffForVoting`) parses the vote count out of the button label
     `"(3)"` and keeps the running total *in the message text*, which it edits in place.
   - `sc_follow_` / `sc_no_follow_` / `*_follow_` read the label.
   - `landUnits_`, `spaceUnits_`, `doneLanding`, `doneRemoving`, `riftUnit_` and `retreatGroundUnits_` accumulate the
     movement/landing summary in the message being edited.
   These need explicit decision state (an accumulator in the pending decision) before they can be typed.
2. **Multi-step flows that edit the message in place.** 384 handlers edit the pressed message's buttons or text
   instead of posting a new prompt. Examples: tactical movement (`tacticalMoveFrom_` -> `unitTactical*` -> `doneWithOneSystem_`),
   landing, hit assignment (`assignHits_` with running remainder), payment (`spend_`/`reduceTG_`/`reduceComm_` -> done),
   SC pre-decline, the whens/afters queue. Model each as **one decision with incremental sub-steps**: a pending
   decision with a mutable `selection` and `options` recomputed after each step, ending with `done`. Not N independent decisions.
3. **Ids without a resolvable target.** See `unknown` above, plus 291 creation sites whose id is assembled at runtime
   from a prefix passed down several calls (`{prefix}`, `{placePrefix}`, `{buttonPrefix}`, `{idPrefix}`,
   `draftable.makeButtonId(...)`, `JimboConst.*`, `CancelGroundHitsButtonId.of(...)`). The generator resolves one level
   of parameter passing; the rest are listed at the bottom of this page.
4. **Sub-routers behind one prefix.** These handlers own a short prefix and dispatch internally, so a single
   catalogue entry hides many decision kinds:
   - `jmfA_` (button, select, modal): the settings-menu framework (Milty, draft system, Franken, mini-Milty), routed by `navId`.
   - `jwds_`: the new draft system (`DraftButtonService` -> `DraftManager.routeCommand`; inner ids belong to each draftable).
   - `componentActionRes_<type>_<id>`: every component action (leader, relic, tech, ability, PN, AC).
   - `fowSetup*`: the fog-of-war setup wizard.
   - `transaction` / `newTransact_` / `send_*`: the trade builder.
   - `generic_button_id_` and `genericReact`.
   - `buttonID.startsWith` (`ButtonHelper.java:4820`) is a literal-string bug: the annotation value is the text `buttonID.startsWith`.
5. **Ephemerals and modals.** About 30 handlers answer with ephemeral buttons (only the presser sees them, for
   example hand-card menus, the "wrong button" notice and peek/look results), and 38 modal handlers plus 45
   `Modal.create` sites take free text (`~MDL` suffix on the button that opens the modal by convention). Ephemerals
   are private sub-decisions of the presser. Modals map to `textInput`, mostly in setup/admin, plus a few in-game
   ones: transaction "Deal Details", notepad, blind selection, custom scoring.
6. **Reaction windows are partly implicit.** "Any player may play a when/after", "everyone pressed No Sabotage", and
   "end turn when all reacted" are tracked through stored values (`game.getStoredValue`, used by 502 handlers) and
   message reactions, not explicit per-player prompts. The Decision stream needs a first-class
   `reactionWindow {eligible[], responded[]}`.
7. **Information buttons are not decisions.** `refresh*`, `show*`, `cardsInfo` and deck viewers (kind `ui:info`), plus
   `deleteButtons` (`ui:dismiss`), should become State queries or be dropped. Undo (`ui:undo`) is an engine command.
8. **Homebrew volume.** About 40% of handlers are homebrew (Theodisi, ACD2, Monuments, Beans, Blue Reverie, Whispers,
   Twilight Kart). They are classified with the same rules, but the `chooseOption` fallback should carry them until
   someone needs them typed.
9. **Classification limits.** `area` and `kind` come from ordered regex rules (`tools/engine-catalog/rules.py`).
   `kindRule` / `areaMatchedOn` show which rule fired. `area-default` and `fields-multi` are weak guesses, and the
   catch-all `tactical/movement` area rule (planet|tile|unit) over-collects faction abilities. Agents should re-home
   entries they own by editing `rules.py` and regenerating, not by hand-editing the JSON.

## Recommended taxonomy

About 30 typed kinds plus primitives and a fallback (full list with option schemas below):

- **Turn flow:** `chooseTurnAction`, `endTurn`, `activateSystem`, `moveUnits`, `landUnits`, `adjustCommandTokens`.
- **Phases:** `pickStrategyCard`, `followStrategyCard`, `resolveStrategyCardPrimary`, `scoreObjective`,
  `discardSecret`, `whenAfterWindow`, `castVotes`, `chooseAgendaOutcome`, `placeRider`.
- **Combat:** `combatRoll`, `assignHits`, `retreat`, `combatModifier`.
- **Economy:** `produceUnits`, `payCost`, `gainOrConvertCommodities`, `transaction`.
- **Cards and components:** `playActionCard`, `sabotageWindow`, `discardActionCard`, `playPromissoryNote`, `explore`,
  `useRelic`, `acquireTechnology`, `useLeader`, `useBreakthrough`, `resolveCardEffect` (a typed multi-step resolution
  keyed by `source`).
- **Setup:** `draftPick`, `chooseFaction`, `chooseColor`, `configureGame`.
- **Primitives**, used as the step type inside `resolveCardEffect` and as stand-alone kinds when an ability asks for
  one thing: `choosePlanet`, `chooseSystem`, `choosePlayer`, `chooseUnit`, `chooseAmount`, `chooseCard`, `confirm`, `textInput`.
- **Fallback:** `chooseOption`, with options `{id, label, tags[], refs{planet?, tile?, faction?, unit?, card?, amount?}}`.
  Tags are semantic hints such as `decline`, `done`, `pay`, `destroy`, `sustain`, `optional`. The bot's label plus
  the parsed id fields are enough to fill `refs` for most legacy buttons.
- **Non-decisions:** `ui:info`, `ui:dismiss`, `ui:undo`, `ui:admin`.

Every decision should carry `{kind, forPlayer | eachPlayer[], source (card/ability/phase), prompt text,
options[] (typed), min/max picks, accumulator (for multi-step), legacyIds[] (the bot ids this replaces)}`.
Keeping `legacyIds` lets the shim keep clicking the legacy button while kinds are migrated one by one.

**Migration order:** turn start (`chooseTurnAction`), `pickStrategyCard`, `followStrategyCard`, `whenAfterWindow` and
`sabotageWindow`, `castVotes`, `scoreObjective`, `assignHits` and `combatRoll`, `moveUnits`, `landUnits`,
`produceUnits` and `payCost`, `transaction`. Together these cover nearly all of the prompts in a normal base/PoK/TE
game. Everything else can ride on `chooseOption` until its area agent types it.
